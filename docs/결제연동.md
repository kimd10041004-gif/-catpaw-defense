# 실제 결제 연결하기

브리지는 **구현돼 있다** — `android/app/src/main/java/com/catpaw/defense/BillingBridge.kt`, Play Billing Library 9.1.0 (U-2).
그래도 지금 상태는 **결제가 연결되지 않은 상태**다. 연결은 코드가 아니라 **Play Console 의 상품**이 켠다.

| 환경 | 지금 동작 |
|---|---|
| 웹 / PWA | `MockBillingProvider` — 버튼을 누르면 캣닢이 지급되고 상점에 **"데모 결제 (실제 청구 없음)"** 이라고 표시된다 |
| 안드로이드 APK · Play Console 에 상품이 없음 | 브리지가 Play 에 붙지만 상품을 못 받는다 → 상점 **"Google Play 결제 (미설정)"** · 구매는 `not_configured` 로 실패 |
| 안드로이드 APK · Play 가 없는 기기(사이드로드·에뮬레이터) | `not_available` 로 실패 · 상점 "(미설정)" |
| 안드로이드 APK · 상품 등록 뒤 | 상점 **"Google Play 결제"** · 버튼에 Play 가 준 실제 가격 · 구매·소모/승인·복원이 Play 로 간다 |

**어느 쪽도 실제로 청구되지 않는 한 청구된 척하지 않는다.** 실패는 코드(`user_canceled` · `pending` · `not_configured` …)와
사람 말로 화면에 그대로 뜬다.

---

## 왜 코드만으로는 안 켜지는가

전부 사람이 계정으로 해야 하는 일이다. 이걸 끝내면 코드는 손댈 것이 없다.

1. Google Play Console 개발자 계정 (등록비 $25, 1회)
2. 앱을 Play Console에 등록하고 **서명된 릴리스 AAB**를 최소 한 번 업로드 (내부 테스트 트랙이면 충분)
3. 판매자 계정(Google Payments) 등록 — 국가·세금·정산 계좌
4. 상품 ID 등록 (아래 §1 — `shop.js` 의 `sku` 와 글자까지 같아야 한다)
5. 라이선스 테스터 계정 등록

## 1. Play Console에 상품 등록

`web/js/domain/shop.js`의 `sku` 값과 **정확히 같은 ID**로 만든다.

| 상품 ID (sku) | 유형 | 참고 (grants) |
|---|---|---|
| `catnip_100` | 소모성 (Consumable) | 캣닢 100개 |
| `catnip_600` | 소모성 (Consumable) | 캣닢 600개 |
| `starter_pack` | 비소모성 (Non-consumable) | 캣닢 300 + 펫 부엉이 + 황금 치즈냥 스킨 (1회) |
| `premium_pack` | 비소모성 (Non-consumable) | 프리미엄 팩 (영구 — 시작 골드·캣닢 2배·주간 보상 2배·훈련 할인) |
| `story_act3` | 비소모성 (Non-consumable) | 시나리오 3막 19~24장 |
| `story_act4` | 비소모성 (Non-consumable) | 시나리오 4막 25~30장 |
| `challenge_pack2` | 비소모성 (Non-consumable) | 도전 팩 2 (규칙 5) |
| `skin_pack_1` | 비소모성 (Non-consumable) | 스킨 3종 (벚꽃 삼색냥 · 설원 샴냥 · 민트 뚱냥) |
| `skin_pack_2` | 비소모성 (Non-consumable) | 스킨 3종 (노을 고등어냥 · 보랏빛 러시안블루냥 · 적갈 턱시도냥) |

비소모성 상품은 `restore()` 가 돌려주는 영수증으로 다시 열린다(`applyPurchase` 가 `grants` 를 적용). 실제 결제 환경에서는
데모 결제로 받은 영구 자격을 `reconcilePurchases` 가 되돌린다 — 캣닢·펫·캣닢으로 산 스킨은 그대로다.

가격은 Play Console에서 정한다. `shop.js`의 `priceLabel`은 화면 표시용 문자열일 뿐이므로
Play Console 가격과 다르면 직접 맞춰야 한다. (정확히 맞추려면 3번의 `queryProductDetails`에서
받아온 실제 가격 문자열을 `describe()`로 웹에 내려주면 된다.)

## 2. 구현된 것 — `BillingBridge.kt` ↔ `domain/billing.js`

의존성은 `android/app/build.gradle.kts` 에 있다: `com.android.billingclient:billing:9.1.0`. Play 는 새 앱에 PBL 8 이상을
요구한다. 코루틴 확장(`billing-ktx`)은 안 쓴다 — 콜백으로 충분하다.

### 계약 (문자열 JSON — WebView 인터페이스는 원시 타입만 안전하다)

| 부르는 쪽 | 무엇 | 답 |
|---|---|---|
| JS → `configure(catalogJson)` | 상품 목록 `[{"sku","consumable"}]`. **`shop.js` 가 단 하나의 출처**다 — 브리지에 sku 를 하드코딩하지 않는다(제출팩의 상품 ID 표가 코드와 어긋났던 일이 있다) | 없음. 연결이 되면 `queryProductDetailsAsync` |
| JS → `describe()` | 지금 상태 | `{"configured","state":"connecting|ready|no_products|unavailable","code","message","prices":{sku:"₩1,200"}}` |
| JS → `purchaseAsync(requestId, sku)` | 결제 화면을 연다 | `CatpawBillingCallbacks.deliver(requestId, json)` — `{"ok":true,"sku","token","orderId"}` 또는 `{"ok":false,"code","message"}` |
| JS → `restoreAsync(requestId)` | 보유 구매 조회 | `deliver(requestId, '[{"sku","token"}, …]')` |
| 브리지 → `CatpawBillingCallbacks.onReady()` | 상품 정보가 도착했다 | 웹이 결제 환경 대조(`reconcilePurchases`)를 한 번 더 돈다 |
| 브리지 → `CatpawBillingCallbacks.onPurchase(json)` | 요청 없이 도착한 구매 (대기 중이던 결제의 승인) | 웹이 복원과 같은 길로 지급한다 |

`isReal` · `label` 은 부를 때마다 `describe()` 를 다시 읽는다 — Play 연결과 상품 조회는 앱이 뜬 뒤에 끝난다.
옛 동기 계약(`purchase(sku)` · `restore()`)도 웹 쪽이 아직 받는다(`purchaseAsync` 가 없는 브리지면 그쪽으로).

### 흐름

- **시작**: `MainActivity` 가 `BillingBridge(activity, webView)` 를 만들어 `connect()` → 웹이 뜨며 `configure(catalog)` →
  연결이 끝나면 `queryProductDetailsAsync(INAPP)` → `onReady`. 상품이 하나도 안 오면 `state: no_products`(= 미설정).
- **구매**: `purchaseAsync` → `launchBillingFlow` → `onPurchasesUpdated`. `PURCHASED` 면 소모품(`catalog.consumable`)은
  `consumeAsync`, 영구 상품은 `acknowledgePurchase`(3일 안에 안 하면 Play 가 환불한다) — 영수증은 그걸 기다리지 않고 바로
  돌려준다. 앱이 그 사이에 죽어도 복원이 미소모 구매를 다시 보고 소모하고, 웹은 토큰으로 중복 지급을 막는다.
  `PENDING`(편의점 결제 등)은 지급하지 않는다 — 승인되면 `onPurchase` 로 온다.
- **복원**: `queryPurchasesAsync(INAPP)` 의 `PURCHASED` 만 돌려준다. 미소모 소모품은 소모하고 미승인 영구 상품은 승인한다.
- **가격**: `describe().prices` 의 실제 가격이 상점 버튼에 뜬다. 없으면 `shop.js` 의 `priceLabel` 자리표시자다.
- **스레드**: `@JavascriptInterface` 는 WebView 스레드에서 불린다. `BillingClient` 는 전부 `runOnUiThread` 로, 답은 `webView.post` 로.

### 여기서 확인 못 한 것 (정직하게)

- 이 개발 세션에는 Android SDK 가 없다. **컴파일은 CI 의 안드로이드 잡이 한다** — 9.1.0 의 API 는 공식 레퍼런스
  (`queryProductDetailsAsync` 의 결과가 `QueryProductDetailsResult` 로 바뀐 8.0 이후 형태)를 읽고 썼다.
- 실제 Play 와의 왕복(결제 시트 · 소모 · 승인 · 복원)은 **라이선스 테스터 계정으로만** 확인된다(§5). 웹 쪽 계약은
  `tests/node/billing.test.mjs` 가 가짜 브리지로 본다.

## 4. 영수증 검증 (돈이 걸린 부분)

`applyPurchase()`는 클라이언트에서 중복 지급만 막는다. **위조는 막지 못한다.**
캣닢이 실제 매출과 연결된다면 서버에서 검증해야 한다:

```
Google Play Developer API
  purchases.products.get(packageName, productId, token)
  → purchaseState == 0 (구매됨) 확인
  → 이미 처리한 token인지 서버 DB로 확인
```

이 게임은 진행도가 기기 로컬(localStorage)에만 있으므로 서버가 없다.
그래서 지금 구조는 **"기기 안에서 잘 동작하는" 수준**이고, 매출 규모가 생기면
계정 시스템과 서버 검증을 먼저 붙여야 한다. 이 한계를 알고 쓰는 것이 중요하다.
